# 会话间通信

已有普通会话和委派子会话通过同一组 MCP 工具通信。目标使用 Codeg 数据库
会话 ID，不使用代理外部 session ID 或委派 task ID。发送方由当前 MCP 认证
连接确定，不能在参数中冒用其他会话。工具随现有委派能力开关启用。

## 发送与回复

```json
{"conversation_id": 42, "message": "请检查刚才的接口参数，完成后回报结果。"}
```

调用 `send_to_session` 后立即返回 `message_id` 和状态，不等待对方回答。
目标忙时默认排队，当前轮结束并完成生命周期处理后，在原代理会话中开启
下一轮。消息包含发送会话 ID，接收方可以用同一工具向来源 ID 回复。

普通会话、父会话、子会话使用相同入口，不需要建立协作关系。首次需要创建
代理会话时，继续使用 `delegate_to_agent`；返回的 `child_conversation_id`
可直接作为后续 `send_to_session` 的 `conversation_id`。首次任务结果仍由
`get_delegation_status` 查询，后续消息的结果由下面的管理工具查询。

## 立即发送

```json
{"conversation_id": 42, "message": "调整任务：先处理类型错误。", "delivery": "immediate"}
```

目标支持原生 steering 时直接投递，消息状态为 `delivered`，处理结果归属
当前运行轮。否则取消当前轮，等待请求及生命周期处理结束，再向同一个代理
会话发送新消息。`delivered` 表示指令已投递，不表示任务已经完成。

## 查询、编辑和取消

向 `manage_session_messages` 提交：

```json
{"conversation_id": 42, "action": "list"}
{"conversation_id": 42, "action": "update", "message_id": "返回的消息 ID", "message": "改为补充异常路径测试。"}
{"conversation_id": 42, "action": "cancel", "message_id": "返回的消息 ID"}
```

只能查询和管理本会话发出的消息。编辑、取消仅作用于尚未执行的 `queued`
消息；与执行认领竞争时，以数据库条件更新为准。多个发送方发给同一目标的
消息共用一个执行队列，立即消息优先，同类消息按持久化顺序处理。

## 排队显示与恢复

消息、执行顺序和结果保存在 SQLite 的 `session_message` 表。聊天输入框
上方的现有排队区域显示待处理消息、来源会话名称和“排队中”；每秒读取后端
状态，刷新后恢复，开始执行后移除。手工消息的原有编辑、删除功能保留，
后端消息仅展示，前端不会再次发送。

重新打开目标会话会检查并唤醒未执行队列。死亡进程已经认领的消息标记为
`interrupted`，不自动重放。恢复检查覆盖目标的所有发送方，防止一条死亡
执行记录阻塞其他会话。已删除发送方的待执行消息不再投递。

离线目标必须成功加载原代理会话才能继续，无法续接时明确拒绝。没有本地
连接且仍标记为运行中的目标不会被接管，需要先重新打开确认其运行状态。
续接普通会话不会应用委派默认模型、模式或发送方的 CLI 运行策略。

会话之间应在有进展、结果或问题时发消息，避免自动互发确认，反复唤醒对方。

## 验证方式

功能验证使用独立数据目录的 `codeg-server` 和浏览器页面，配合真实 MCP
伴生进程及 ACP 代理。禁止编译或启动桌面客户端作为测试对象。
